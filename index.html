THE IDEA
After coming back from Tokyo, I kept thinking about all the cool cars I saw there, and wanted to make a game about them. And since drifting originated in Japan, so a game centered around Japanese car culture just made sense. Then I thought about what would capture that feeling well, and based on what I saw and took photos off, I knew that I wanted a neon city with graffiti but haven't added it yet.. but for now I have a drift track with hills.
Also, before this I wanted to make a drifting game to see how I could build smooth drifting physics and how car physics actually work as I enjoyed playing these types of games. The drifting physics took a lot of iterations to make it feel right and to make it behave how an actual car would.

01
WHAT'S UNDER THE HOOD
no pun intended.
PHYSICS
Vehicle Physics
The base vehicle simulation is handled by UE5's Chaos Vehicle physics system. So Car has custom engine, transmission, differential setups and the wheels with lateral slip curves, suspension, and torque configs similar to their real world counterparts.
DRIFT SYSTEM
Arcade drifting
I wanted the drift to feel arcadey, so that required a component on top of Chaos physics to reduce the realism and make it fast paced. This system has counter steering, applies drift force, adjust torque and angular damping to get the arcade feel.
environment
drift track
Drift track as the environment of the game - japan themed with kanji and hiragana markings with mountain and nature environment, then edit to sustained drift angles around corners with wide sand runoff zones and cones placement.
scoring SYSTEM
Score
The Scoring system is designed to reward controlled and dedicated drifts with different multiplier based on which gear the car is on, score points depending upon tilt of the car with continuous drift meter drain.
CAMERA
Dynamic Spring Arm
The camera tilts and lags based on MPH and drift angle, and FOV change ofcourse. When the car is in a drift, the spring arm rotates dynamically to capture the drift perfectly. Camera system to change perspective from behind car to driver or rear perspective.
VFX & SFX
Skid marks & Engine sound
Niagara particle systems on each wheel emit skid marks based on drift angle and speed. Meta-sound system for the engine and skid sound, which changes based on RPM, drift angle.
02
CHALLENGES & SOLUTIONS
01
Chaos Physics Fighting Me on Rear Traction
UE5's Chaos vehicle system isn't built for drifting. No matter how much you tweak Chaos Vehicle's exposed parameters, it doesn't produce real drift. Chaos vehicle marks drifting as slip and reduces both lateral and sideways speed equally, resulting in dead drifts. After the physics tweak on top of the chaos physics and other tweaks inside chaos physics like center of mass, engine and wheel setup.
Instant slowing down when entering drift, resulting in dead drift
Dynamically change angular damping and apply force for arcade feel and better drift.

Stepped Animation
Animation trick used mainly in 2D looking 3D animations like used in Spider-Man: Across the Spider-Verse, which is animated using stepped keyframes, which is somewhat similar to stop motion animation, and to some extent you can use this in your retro game for a unique animation style. So what does this mean, for example you are animating on 3s it just means the next animation frame will be after 3 frames of that constant frame, so no in-betweens or transitions frame
2s - 2 constant frame
3s - 3 constant frame and so on
3s Animation Demo
step_animation.py — Blender Keyframe Stripper
Python
import bpy

step = 2 ## determines the step

obj = bpy.context.active_object

if obj and obj.animation_data and obj.animation_data.action:

    action = obj.animation_data.action

    for fcurve in action.fcurves:

        keys = fcurve.keyframe_points

        # remove keys except every nth
        for i in reversed(range(len(keys))):
            if i % step != 0:
                keys.remove(keys[i])

        # set constant interpolation
        for kp in keys:
            kp.interpolation = 'CONSTANT'

    # refresh UI
    for area in bpy.context.screen.areas:
        if area.type in {'DOPESHEET_EDITOR', 'GRAPH_EDITOR'}:
            area.tag_redraw()

else:
    print("Select an object with animation.")

01
32,768 Colors Still Banded
Well why do we even need dither, isn't 32,768 a lot a color? No, I thought that too but I was wrong, even with these many colors you could still see color banding (not a smooth gradient between colors) once quantized down from Godot's 8 bit output. So a ColorRect shader grabs the rendered frame through the screen texture, divides each channel into 32 steps, and nudges every pixel by an offset pulled from a 4×4 ordered dither matrix before rounding - the noise is intentional, it simulates the sense of having more colors then there actually is and breaks up the banding.
dither.gdshader — 15-bit Color Quantize
GDShader
shader_type canvas_item;

uniform sampler2D screen_tex: hint_screen_texture, repeat_disable, filter_nearest; // get what is being rendered, tells Godot to not tile it and use pixel-perfect sampling so it doesnt get blurry

// 4×4 ps1 ordered dither matrix, it hold the offset values that gets applied to each pixel depending on its screen postion
const float dither[16] = float[16](
  -4.0,  0.0, -3.0,  1.0,
   2.0, -2.0,  3.0, -1.0,
  -3.0,  1.0, -4.0,  0.0,
   3.0, -1.0,  2.0, -2.0
);

void fragment() { // fragment func lets you manipulation each pixel
  vec3 screen_color = texture(screen_tex, UV).rgb; // get the rgb color of the pixel

  // this gets where the pixel sit in the dither matrix
  int x = int(FRAGCOORD.x) % 4; // FRAGCOORD is the pixel's actual 2D screen postion and % get it to 0 to 3 range
  int y = int(FRAGCOORD.y) % 4;
  int index = y * 4 + x; // converts 2D coordinates into a flat array index

  float dither_offset = (dither[index] / 8.0); // gets the offset

  vec3 quantized_color = floor((screen_color * 255.0) / 8.0 + dither_offset) / 31.0; // quantizes 8bit color with dither offset to a 5bit color

  COLOR = vec4(quantized_color, 1); // applies the color and 1 is the alpha value
}
▲ screen-space dither pass, applied on a Color Rect material over the whole frame
02
Modern GPUs Are Too Precise
Jitter effect, Why does this happen? The ps1 hardware rasterizer was unable to render polygons at a sub pixel level due to lack of precision to calculate positions between pixels so it only worked with integers and rounded off the floating point numbers, which caused them to appear snapping at lower resolution. Modern gpus can accurately calculate to sub pixel level and render at higher res, so that wobble just doesn't happen anymore, it has to be forced back in. You have to add a material override for every material and model, converting each vertex to normalized device coordinates, rounding it to a fake low resolution, then converting it back before handing the position off to the rasterizer.
Vertex jitter at rasterization - polygons snapping to a fake low-res grid
ps1_jitter.gdshader — Clip-Space Vertex Snap
GDShader
shader_type spatial;
render_mode blend_mix, cull_back, depth_prepass_alpha,
  shadows_disabled, specular_disabled, vertex_lighting; // these just strips the modern rendering features

uniform sampler2D base_tex: source_color, filter_nearest; // Its a parameter in the shader for the material base color
uniform vec2 texture_tile = vec2(1, 1); // tiles the texture
uniform vec2 texture_offset = vec2(0, 0); // offset if needed

uniform bool snap_enabled = true; // should have jitter effect?
uniform float snap_res: hint_range(60.0, 480.0, 1) = 128.0; // smaller value more jitter, fake resolution for vertex positions

void vertex() { // runs for every vertex in a mesh and lets you manipulate it, we are reversing the modern rendering pipeline so we can inject our code into it
  vec4 view_space_pos = MODELVIEW_MATRIX * vec4(VERTEX, 1.0); // object space to view space
  vec4 clip_space_pos = PROJECTION_MATRIX * view_space_pos; // view space to clip space

  if (snap_enabled) {
    vec2 ndc = clip_space_pos.xy / clip_space_pos.w; // converts it into NDC (Normalized Device Coordinates, the –1 to +1 screen space) by dividing it by the forth direction of the modern clip space w
    ndc = round(ndc * snap_res) / snap_res; // locks the vertex to one of the point in the fake res across the screen
    clip_space_pos.xy = ndc * clip_space_pos.w; // converts back to clip space
  }
  POSITION = clip_space_pos; // sets the postion
}

void fragment() { // in fragment shader we are only applying back the textures
  vec4 base = texture(base_tex, UV * texture_tile + texture_offset);
  ALBEDO = base.rgb;
  ALPHA = base.a;
}
▲ material override applied to every mesh in the scene
03
Smooth Lighting Broke the Illusion
Godot's default lighting is calculated pixel to pixel, which gives a smooth gradient - exactly what gives away a modern engine. rendering/shading/overrides/force_vertex_shading = true | forces the lighting to be at vertex level instead, so each triangle just gets one lighting value interpolated across its face, the same faceted look original hardware was stuck with.
Godot's default pixel shading (left) vs Vertex shading (right)
03
WHAT I LEARNED
How graphic engine works
I learned a lot about how does graphic engine works, mainly how does it translate 3D graphics to 2D graphics and mainly the rasterizer, ndc space.
THE PS1 GPU WAS TECHNICALLY A 2D RENDERER
PS1 GPU was technically a 2D rasterization engine, it didn't have a native 3D depth buffer (Z-buffer) or hardware support for perspective correction, it relied on a separate companion chip called the Geometry Transformation Engine. The GTE handled 3D math and projections, converting 3D world coordinates into flat 2D screen coordinates then fed it to the 2D GPU.
ARTISTIC CHOICE or Workarounds
Many retro games made choices some workaround, some artistic choices and some both like - Capcom used fixed camera because they wanted to have prerendered background for immersion and have cinematography that changes the mood throught fixed camera angles. These game could only have one light source at a time and derived most of the light from AO maps (prebaked lighting from real world places). Silent Hill iconic fog was originally a workaround for technical limitations like limited draw distance and low hardware processing power.
04
WHAT'S NEXT

Gives distorted texture mapping because PS1 hardware mapped mapped textures in 2D screen space instead of accounting for 3D depth, but most of the games tried to hide this using vertex color rather than textures, having high density models, fixed camera angles. So, I'm not sure if I want to add this into the game. Also its distracting.

Add a CRT filter. If you have an old T.V the dithering effect looks so good already, so a crt filter over the dithered, jittered output would make it cooler and really give that retro feel.

Action System
Start and Stop of Actions with networking
Action Component is an Actor Component that handles the start and stop of an action. It cycles through the action array and matches the Gameplay tag to start/ stop the action.
SActionComponent.cpp
C++
void USActionComponent::ServerStartAction_Implementation(AActor* InstigatorActor, FGameplayTag NameTag)
{
    StartActionByName(InstigatorActor, NameTag);
}

bool USActionComponent::StartActionByName(AActor* Instigator, FGameplayTag NameTag)
{
    SCOPE_CYCLE_COUNTER(STAT_StartActionByName); 
    UE_LOG(LogTemp, Warning, TEXT("StartActionByName called with: %s, Actions.Num=%d"), *NameTag.ToString(), Actions.Num());

    for (USAction* Action : Actions)
    {
        if (IsValid(Action) && Action->GetNameTag() == NameTag)
        {
            if (!Action->CanStartAction(Instigator))
            {
                continue;
            }
            if (!GetOwner()->HasAuthority())
            {
                ServerStartAction(Instigator, NameTag);
            }
            else
            {
                Action->StartAction(Instigator);
            }
            
            TRACE_BOOKMARK(TEXT("StartAction: %s"), *GetNameSafe(Action));
            return true;
        }
    }
    return false;
}

void USActionComponent::ServerStopAction_Implementation(AActor* InstigatorActor, FGameplayTag NameTag)
{
    StopActionByName(InstigatorActor, NameTag);
}

bool USActionComponent::StopActionByName(AActor* Instigator, FGameplayTag NameTag)
{
    for (USAction* Action : Actions)
    {
        if (IsValid(Action) && Action->GetNameTag() == NameTag)
        {
            if (Action->GetIsActionRunning())
            {
                if (!GetOwner()->HasAuthority())
                {
                    ServerStopAction(Instigator, NameTag);
                }
                else
                {
                    Action->StopAction(Instigator);
                }
                return true;
            }
        }
    }
    return false;
}
Actions
Actions are UObject derived classes that can be added to action component to grant the pawn the ability to do that action and it handles the CanStart/Start/Stop using Gameplay Tags.
SAction.cpp
C++
bool USAction::CanStartAction_Implementation(AActor* Instigator)
{
    if (GetIsActionRunning())
    {
       return false;
    }
    
    USActionComponent* ActionComp = GetOwningComponent();
    
    if (ActionComp->ActiveGameplayTags.HasAny(BlockedTags))
    {
       return false;
    }
    return true;
}


void USAction::StartAction_Implementation(AActor* Instigator)
{
    UE_LOG(LogTemp, Log, TEXT("Running Action: %s"), *GetNameSafe(this))
    
    USActionComponent* ActionComp = GetOwningComponent();
    
    ActionComp->ActiveGameplayTags.AppendTags(GrantsTags);
    
    bIsActionRunning = true;
}

void USAction::StopAction_Implementation(AActor* Instigator)
{
    UE_LOG(LogTemp, Log, TEXT("Stopped Action: %s"), *GetNameSafe(this))
    
    USActionComponent* ActionComp = GetOwningComponent();
    ActionComp->ActiveGameplayTags.RemoveTags(GrantsTags);
    
    bIsActionRunning = false;
}
▲ checks blocked tags before an action can run, then grants/removes gameplay tags while the action is running.

void USCheatManager::HealSelf(float Amount)
{
    APlayerController* MyPC = GetOuterAPlayerController();

    if (APawn* MyPawn = MyPC->GetPawn())
    {
        USAttributeComponent* AttributeComp = USAttributeComponent::GetAttributes(MyPawn);
        
        if (Amount < 0)
        {
            Amount = AttributeComp->GetMaxHealth();
        }
        AttributeComp->ApplyHealthChange(MyPawn, Amount);
    }
}

void USCheatManager::DamageSelf(float Amount)
{
    APlayerController* MyPC = GetOuterAPlayerController();

    if (APawn* MyPawn = MyPC->GetPawn())
    {
        USAttributeComponent* AttributeComp = USAttributeComponent::GetAttributes(MyPawn);
        
        if (Amount < 0)
        {
            Amount = AttributeComp->GetMaxHealth();
        }
        AttributeComp->ApplyHealthChange(MyPawn, -Amount);
    }
}

void USCheatManager::GrantCoin(int32 Amount)
{
    APlayerController* MyPC = GetOuterAPlayerController();

    if (APawn* MyPawn = MyPC->GetPawn())
    {
        ASPlayerState* SPlayerState = MyPawn->GetPlayerState<ASPlayerState>();
        if (IsValid(SPlayerState))
        {
            SPlayerState->ApplyCreditChange(MyPawn, Amount);
        }
    }
}

void USCheatManager::KillAll()
{
    APlayerController* MyPC = GetOuterAPlayerController();

    if (APawn* MyPawn = MyPC->GetPawn())
    {
        for (TActorIterator<ASAICharacter> It(GetWorld()); It; ++It) 
        {
            ASAICharacter* Bot = *It;
            USAttributeComponent* AttributeComp = USAttributeComponent::GetAttributes(Bot);
            if (AttributeComp && AttributeComp->GetIsAlive())
            {
                AttributeComp->Kill(MyPawn);
            }
        }
    }
}

void USCheatManager::MoveInDirectionBy(float ByCm, ::EMoveAxis Axis)
{
    APlayerController* MyPC = GetOuterAPlayerController();

    if (ACharacter* MyCharacter = MyPC->GetCharacter())
    {
        if (UCharacterMovementComponent* MoveComp = MyCharacter->GetCharacterMovement())
        {
            MoveComp->Velocity = FVector::ZeroVector;
        }
        FVector Direction = FVector::ZeroVector;

        switch (Axis)
        {
        case EMoveAxis::X:
            Direction = MyCharacter->GetActorForwardVector();
            break;
        case EMoveAxis::Y:
            Direction = MyCharacter->GetActorRightVector();
            break;
        case EMoveAxis::Z:
            Direction = FVector::UpVector;
            break;
        }
        
        MyCharacter->AddActorWorldOffset(Direction * ByCm, false);
    }
}
